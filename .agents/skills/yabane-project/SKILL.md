# Yabane 项目原则

Yabane 的目标不是复制一个大而全的 AI 平台，而是提供一个小型、高性能、行为可预测的 LLM Gateway。

## 为什么做 Yabane

现有网关常根据模型名称或通用能力表猜测上游行为，并在请求途中静默归一化、删除或改写参数。这会导致客户端表达的意图与实际发给 Provider 的请求不同，而且问题只在特定模型和协议组合下出现。复杂抽象也会掩盖上游错误，让排查网关、Provider 和模型之间的责任边界变得困难。

Yabane 因此优先解决三个问题：

1. **行为透明**：默认忠实转发请求和上游响应，不基于模型名猜测能力，不做隐式降级。
2. **结果可解释**：保留上游状态码和错误信息；发生任何转换时，都必须由显式配置或明确的协议适配触发，并且能够观测。
3. **保持精简**：只实现已经出现的真实需求，不因为其他网关拥有某项能力就复制它。

## 开发决策

- 优先保证热路径性能：使用 Rust、异步 I/O、连接复用和流式转发，避免在无需转换时解析或缓冲请求与响应体。
- Provider 能力必须来自用户配置或 Provider 自身的权威元数据；不能仅凭模型名称推断后静默修改请求。
- OpenAI Chat Completions、OpenAI Responses 和 Anthropic Messages 是独立协议表面。协议内代理默认透传；未来的跨协议转换必须显式启用并有独立测试。
- 管理页面用于配置和理解网关，不应成为复杂控制平面。信息架构和交互保持 Google Admin Console 式的清晰、克制和面向操作，但不要照搬其平淡的视觉表现；页面必须反映 Provider → Endpoint → Key 的资源层级，优先使用结构化编辑器、内联校验和可观测摘要，而不是暴露原始 JSON 或把不同层级的操作平铺。
- 新功能应尽量独立加入。若一个需求必须引入数据库、多租户、计费、插件系统或分布式协调，先确认当前版本确实需要这些复杂度。

## 视觉语言

Yabane 的视觉个性是“清晰、快速、年轻，但不轻浮”。设计管理页面时遵守以下原则：

- 从 Yabane 双箭头标志延伸视觉元素：使用大尺度高对比色块、斜向切面、不对称构图和少量路由轨迹线，表达方向、推进和连接。不要改用与品牌无关的装饰圆球、柔和光斑、通用渐变或插画。
- 图标必须保留“双箭头向前”这一核心识别资产，可以用切角轮廓、明暗切面和有限强调色增强年轻感，避免退回通用渐变圆角方块。任何版本都要同时在 16px favicon、常规导航尺寸和 About 单色场景下清晰可辨。
- 让背景有动势，让操作区保持稳定。登录、首次设置、About、空状态和页面留白可以更有表现力；表单、表格、编辑器和数据卡片必须保持规整、高对比和易扫描，不能把斜线或动画带进需要精确操作的内容层。
- 使用深墨色、Yabane 蓝和冷白建立主要明暗对比，以青色等冷色作有限补充。颜色需要形成明确层级，不能只堆叠同一蓝色色阶，也不要牺牲文本、边界和状态颜色的可读性。
- 动态只用于大型背景切面或轨迹，采用缓慢、低幅度的位移，制造“画面是活的”而不是持续吸引注意。装饰图形必须不接收输入、对辅助技术隐藏，并在 `prefers-reduced-motion` 下停止动画。
- 响应式布局允许背景图形被有意裁切，但品牌方向感和内容焦点必须保留；不能产生横向滚动、遮挡控件或让文字落入低对比区域。
- 评审视觉改动时同时检查稀疏页面和高密度页面：前者不能显得空白无设计，后者不能因品牌装饰降低工作效率。

## 评审标准

评审每项改动时先问：

1. 它是否在未明确配置的情况下改变客户端请求？
2. 上游收到的内容以及发生的转换是否可验证？
3. 上游错误是否仍能原样定位？
4. 非转换路径是否继续保持流式、低拷贝和低延迟？
5. 这项复杂度是否由当前真实需求驱动？

如果答案不符合上述原则，优先简化设计，而不是增加更多启发式规则来掩盖问题。
