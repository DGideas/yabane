# Yabane Gateway Behavior Checklist

This file is the source checklist for end-to-end gateway behavior. Every item begins with `*` so it can be converted into automated E2E cases.

## Service and administration

* Yabane loads local environment configuration from `.env` when present while preserving variables already supplied by the process environment.
* `yabane --help` and `yabane --version` print help or Git commit/time build information and exit without loading configuration or starting the server; Yabane does not present an application version, and unknown or malformed command-line arguments fail visibly.
* Yabane listens on the address passed through `--addr`, defaulting to `127.0.0.1:8080`; the listen address is intentionally not configured through an environment variable.
* `GET /healthz` returns `200` and does not require a gateway API key.
* The web admin console uses a separate administrator session and never accepts gateway API keys as admin authentication.
* Admin HTML, CSS, JavaScript, and the faceted Yabane SVG application icon are embedded in the binary and disable browser caching so a restarted local binary does not leave stale console resources.
* The console exposes the Yabane Git commit, commit time, and bundled MIT license information from a desktop sidebar footer that remains fixed beneath the sticky top bar while page content scrolls, and from the account menu on narrow layouts; it does not present an application version. The About dialog identifies Yabane as an open source LLM gateway, uses a stationary high-contrast Yabane mark over an animated, restrained ink-blue and muted-cyan faceted backdrop while respecting reduced-motion preferences, and links to the project GitHub repository.
* On first use, the console requires creation of the single administrator with username, email, and a password of at least eight characters; concurrent setup attempts are serialized so only one administrator can be persisted.
* After setup, unauthenticated visitors see a responsive, brand-faceted login screen with a high-contrast form panel, the username-or-email field receives initial focus, and they can sign in with username or email plus password; first-use administrator registration shares the same visual system and initial username focus, while decorative artwork is inert and respects reduced-motion preferences.
* Administrator passwords are persisted only as Argon2 password hashes.
* Successful setup or login creates an HttpOnly, SameSite=Strict session cookie with a 24-hour server-enforced lifetime; expired sessions are removed from memory, and logout revokes the current session.
* API Access and each Provider detail page expose the getting-started guide; the guide groups Pi, OpenCode, Claude Code, Codex, and VS Code Copilot guidance behind an Agent selector shown only on the Agent setup tab, alongside selector-free Generic Agent values and Shell/test-request tabs; switching between differently sized tabs smoothly animates the content height without a delayed layout jump, and the guide uses current Gateway URLs, discovered `provider/model` IDs, public route aliases, and Gateway API keys to generate copyable setup instructions without exposing upstream credentials, explicitly identifies VS Code Copilot as unsupported for arbitrary custom base URLs unless an extension provides that capability, and explains Yabane's explicit cross-protocol conversion behavior. API Access also shows a copyable `GET /v1/models` example.
* The top-right administrator avatar opens an account menu showing the signed-in username and email, with explicit Manage profile and Sign out actions.
* An administrator session can update its username and email from the profile dialog; changing the password additionally requires the correct current password and a new password of at least eight characters, and Gateway API keys cannot modify the administrator profile.
* Protected `/admin/*` APIs return `401` without a valid administrator session, while session, setup, login, static resources, and health remain public.
* Initial administrator setup does not require a CAPTCHA.
* Login requires a Cloudflare Turnstile token only when both a secret and a matching site key are available; the backend validates success, the `login` action, and an allowed hostname with Siteverify, while an unconfigured or incomplete Turnstile configuration disables CAPTCHA.
* The login console renders Turnstile with `TURNSTILE_SITE_KEY`; when the always-pass Turnstile test secret is configured and no site key is specified, it uses Cloudflare's matching test site key so local verification works without a production widget.
* Provider, gateway authentication, administrator, model-route, and per-Extension enabled-state configuration is persisted under `data/`, restored after restart, and replaced through a synced temporary file plus rename so interrupted writes do not expose partial JSON.
* The Providers top-level page presents a concise provider list with content-width `provider/model-id` examples that do not stretch to the Provider name width; selecting one provider opens a visually distinct Provider settings page with breadcrumb context, a Provider identity summary, Provider-wide settings, and a separate child-endpoint hierarchy.
* A Provider's display name can be edited independently after creation without replacing omitted Provider settings, while its Provider ID remains immutable because it is the public model prefix referenced by Gateway API-key scopes, model routes, request URLs, and Activity; the edit dialog presents that ID with an explicit Permanent badge, lock treatment, and non-editable styling, and explains this distinction instead of implying that deletion is the only Provider-level operation.
* Provider details visually nest upstream API keys inside their owning Endpoint, and key-creation actions name and preselect that Endpoint so Provider, Endpoint, and key actions are not presented as peers.
* The sidebar selection background and blue indicator animate when switching top-level sections. On narrow layouts, a touch-sized menu button opens that same navigation as an accessible drawer; selecting a destination, pressing Escape, or activating the backdrop closes it without losing the current page.
* Settings search finds top-level settings, provider-model discovery, gateway-key generation, and configured providers, visibly selects the active result, supports Arrow Up/Down, Home/End, Enter, and Escape from the combobox, then navigates to the selected result.
* Home, Providers, provider details, model routing, Extensions, API access, Activity, and login have distinct browser URLs that can be opened directly and support browser Back/Forward navigation.
* The Extensions page lists the trusted native Rust extensions compiled into the current binary, their enabled state, versions, Extension API versions, declared Hook stages, and implementation type without implying that arbitrary runtime code can be installed; an administrator can persistently enable or disable each compiled Extension without deleting its configuration, and the page links to the public Extension development guide, shows copyable default-build, runtime `--no-extensions`, and Core-only build commands even when no Extension is included, and may derive resource-scoped configuration summaries from the same Provider data used by the Request Defaults editor and OpenAI subscription Endpoints. An Extension that implements an Endpoint type cannot be disabled while configured Endpoints depend on it.
* The bundled Traffic Capture Extension is stopped by default and provides an explicit Provider/Endpoint-scoped, next-N request capture session with an idle deadline, bounded bodies, additional Header redaction, and 1-to-30-day retention; its separate console lists, manually refreshes, inspects, and deletes captures, clearly labels upstream request and response wire data, and warns that prompts, files, tools, and model output may be sensitive. An active session must be stopped before disabling the Extension or deleting its scoped Provider or Endpoint, preventing a configured capture from becoming silently inert or orphaned.
* `--no-extensions` disables all compiled Extension Hooks for that process without changing their persisted enabled states; the Extensions API and console still list the compiled implementations, identify the startup override, and do not allow runtime enablement until Yabane restarts without the option.
* Authenticated console pages use the full width available beside the sidebar with responsive horizontal gutters, rather than remaining capped to a narrow fixed content column on wide displays. Their main workspace uses a subtle animated Yabane faceted backdrop and elevated content surfaces without reducing readability, intercepting input, or ignoring reduced-motion preferences.
* Console dialogs remain contained within desktop, tablet, and iOS-sized visual viewports, use one-column controls where needed, provide touch-sized actions, account for safe-area insets, and keep headers and actions reachable while long content scrolls; responsive E2E runs desktop/tablet in Chrome and iPhone-sized layouts in WebKit.
* Empty configuration collections use a consistent illustrated state with an in-context next action; API access and Management API key empty states open the same creation flows as their page-level actions.
* The authenticated Home page uses a responsive Yabane route-themed hero, visualizes the last 24 hours of request and token usage, links to Activity and configured providers, and automatically refreshes its statistics while the page and browser tab are visible; decorative motion is inert and stops under reduced-motion preferences.
* Gateway API keys authenticate inference requests and model listing with provider scopes, while Management API keys authenticate the control API; administrator profile and Management-key endpoints require a browser session.
* Each administrator can create named Management API keys beginning with `yab_mgmt_`, with optional expiry; the secret is shown once, only its hash is persisted and compared in constant time, last-use times are tracked, and revocation is immediate.
* The embedded live API reference at `/docs` renders the bundled OpenAPI specification served at `/openapi.json` and can execute requests against the running instance using the browser session or a pasted Bearer key.
* Boolean settings use accessible animated switches or check controls instead of the browser's default checkbox presentation, and conditionally revealed form fields animate their height and opacity instead of abruptly changing the dialog layout.
* Forms visibly identify required and optional fields.
* Provider-scope selection uses individually labeled checkboxes and an empty selection clearly means unrestricted access.
* Secret-entry fields use the same Show/Hide interaction throughout the admin console.
* Upstream-key traffic distribution is presented as percentages that must total 100% across enabled keys; newly added keys use the standard default weight, while the stored positive weights preserve deterministic weighted round robin.
* The Model routing page explains that rules bind matching models to a specific Endpoint and upstream credential, shows exact and prefix examples, and makes clear that unmatched models retain default Endpoint credential selection; each configured rule keeps the public model identity compact regardless of destination count and visually separates its match type, destination count, upstream model, Endpoint, credential, active status, and normalized traffic percentage instead of presenting the destination as an undifferentiated text string.
* Missing configuration files produce empty/default configuration; malformed or unreadable configuration, including duplicate Provider, Endpoint-within-Provider, key-within-Endpoint, Gateway API-key, Management API-key, or model-route identities, fails startup visibly instead of silently overwriting or ambiguously addressing resources.
* `YABANE_LOG` controls logging, defaults to `info`, and an invalid filter fails startup.

## Gateway authentication

* Gateway API-key authentication is enabled by default.
* An administrator can enable or disable gateway API-key authentication globally.
* When authentication is disabled, `/v1/*` requests do not require `Authorization`.
* When authentication is enabled, every `/v1/*` request without an `Authorization: Bearer <key>` header returns `401`.
* When authentication is enabled, a malformed authorization header returns `401`.
* When authentication is enabled, an unknown or deleted gateway API key returns `401`.
* An expired gateway API key returns `401`.
* A valid non-expired gateway API key authorizes requests within its provider scope; downstream model listing and inference routing use the scope established by authentication middleware rather than re-reading caller credentials.
* A gateway API key with an empty provider scope can access every configured provider.
* A provider-scoped gateway API key receives `403` when an inference request selects a provider outside its scope.
* `GET /v1/models` returns only models belonging to providers allowed by the gateway API key.
* Generated gateway API keys begin with `sk-` and use cryptographically secure random bytes.
* A generated gateway API-key secret is returned by the create operation and remains available to authenticated administrators in subsequent list operations.
* The generated-key dialog and API-key list provide Copy API key actions with a standard copy icon and visible success feedback; existing keys are identified in the list by a short masked prefix rather than displaying or embedding the full secret in the page markup.
* Gateway API-key secrets are persisted so the administrator can copy them later without displaying the full value in the API-key list; their SHA-256 hashes are also retained and compared in constant time for request authentication.
* Gateway API keys support an optional note, optional expiration time, and optional provider allowlist; administrators can patch any subset of those fields without resetting omitted values or changing the key secret, and the console visibly marks expired keys.
* Creating or editing a gateway API key with an expiration time in the past is rejected with `400`; an expired key can be reactivated only by editing it to have no expiry or a future expiry.
* Creating or editing a gateway API key with an unknown provider in its allowlist is rejected with `400`.
* Deleting a gateway API key revokes it immediately.

## Provider routing and proxying

* Inference requests select a provider from the `provider/model` request model ID.
* Only the first model path segment is removed; the remaining namespaced upstream model ID is preserved.
* A model without a provider prefix is rejected with `400`.
* An unknown provider prefix is rejected with `400`.
* A provider with no Endpoint exposing the requested model is rejected with `400`; when model discovery has not established Endpoint availability, any configured Endpoint remains eligible.
* Routing first chooses an Endpoint native to the caller's API surface, then deterministically falls back to another Endpoint exposing the same model and applies Yabane's explicit cross-protocol adapter; an explicit model-route target always takes precedence.
* OpenAI Chat Completions requests are accepted only at `POST /v1/chat/completions`.
* OpenAI Responses requests are accepted only at `POST /v1/responses`.
* Anthropic Messages requests are accepted only at `POST /v1/messages`.
* Request fields other than the provider prefix in `model` are forwarded without semantic rewriting on a native protocol path unless an explicitly configured request extension modifies them, except that OpenAI subscription Endpoints explicitly adapt the public Responses request to pi-ai's ChatGPT Codex request shape: they require streaming upstream, force `stream: true` and `store: false`, include `reasoning.encrypted_content`, apply defaults for missing instructions, text verbosity, tool choice, and parallel tool calls, move a leading string-content `developer` or `system` input into `instructions`, convert the standard Responses string-input shorthand to its equivalent user-message form, and omit the unsupported public `max_output_tokens` field.
* Cross-protocol requests explicitly selected by calling a non-native API surface map shared message roles, text, image, and document/file content, system instructions, function tools, tool choice, tool calls/results, output limits, supported stop sequences and sampling controls, streaming intent, structured-output formats, and usage fields; document sources preserve their URL, data, file ID, and filename in the target wire shape, while known source-protocol fields and built-in tools with no target-protocol equivalent are not forwarded, invented, or inferred.
* OpenAI subscription Endpoints accept all three caller surfaces through the explicit adapter, while their upstream connection remains streaming OpenAI Responses.
* The versioned native Extension API v1 lets compiled Extensions register Provider-specific Endpoint metadata, models, subscription OAuth lifecycle, and final wire preparation while Core retains resource routing, persistence, credential ownership, and redaction; it also provides ordered upstream-request and upstream-header Hook chains: each Hook sees earlier modifications, a structured rejection is attributed to its extension instance, stops later Hooks, and prevents the upstream request; invalid, failed, or panicking Hook execution is likewise attributed and fails closed without exposing its internal error to the caller. It also provides read-only upstream-exchange observers over final request data, response headers, streaming chunks, and completion outcome; observer failure never changes the proxied result, and a build or runtime configuration with no enabled Hooks preserves the normal proxy path without dispatching extension work or allocating observer header snapshots.
* Core irreversibly redacts upstream authentication, cookies, subscription identity, and request-affinity Header values before exposing an exchange to an Extension; it constructs those snapshots only when an observer's cheap synchronous preflight declares interest and initializes that preflight-selected Hook set without re-evaluating mutable interest state. Traffic Capture bounds each request and response body without buffering the proxy stream, persists content outside Activity, and records truncation or interruption explicitly. Its read-only upstream-exchange observer sees the final upstream request and raw upstream response incrementally, cannot modify or reject traffic, and observer failures never alter the proxied response.
* Extension header Hooks operate on a separate overlay before Core adds upstream authentication; authentication, cookies, subscription identity, and hop-by-hop headers remain Core-managed and cannot be supplied by an extension. Exchange observers receive credential-redacted header snapshots: authorization, API keys, cookies, subscription account identity, proxy authentication, and request-affinity identifiers are never exposed to them.
* The built-in Traffic Capture Extension is an explicitly Provider-and-Endpoint-scoped, count-limited, time-limited diagnostic facility that stores bounded upstream request and response bodies separately from Activity; it is inactive by default, requires an enabled Extension and a future expiry before capture can start, always redacts Core-managed credentials, supports additional header redaction, reports truncation, observer drops, and failed exchanges, stores capture files through private synced atomic replacement, serializes count-state persistence so stale asynchronous writes cannot reactivate or extend a newer capture session, drains pending capture writes before deletion or graceful-shutdown flushes so deleted records cannot be resurrected by an older queued write, automatically removes expired captures from memory and disk, and publishes captures in memory only after successful persistence, counting a failed write as one dropped capture. Administrators can inspect or delete captures without allowing failed persistence to make memory claim success. Activity itself continues to retain no prompt or response content.
* The built-in Request Defaults extension lets Provider-level extra headers and JSON request-body fields apply to every current and future endpoint or to an explicit non-empty selection of that Provider’s endpoints; endpoint-level values override matching provider-level values where the Provider defaults apply.
* The Provider page identifies Request Defaults as an extension-provided request modification while retaining its structured header and body-field editor in Provider context; when included it presents its enabled or disabled state and the Configure action without a redundant Extensions-page link, and when disabled it uses a prominent warning treatment that explicitly says saved values are not applied to upstream requests; when absent it disables configuration and links to build instructions. The editor offers all-endpoint and selected-endpoint scope controls, validates endpoint selection, duplicate names, HTTP header syntax, reserved authentication and hop-by-hop headers, and each body field’s JSON value before saving, and shows a live JSON body preview.
* Upstream status codes and error response bodies are visible to the caller; successful cross-protocol responses use the caller's selected response envelope and include `x-yabane-protocol-conversion` naming the upstream-to-caller conversion.
* Native-protocol response bodies, including SSE, are streamed without full response buffering; cross-protocol SSE is converted incrementally, retaining completed output only when a non-streaming caller or the target Responses terminal event requires it, and rejects an individual unterminated SSE frame larger than 8 MiB. Cross-protocol non-streaming JSON responses are buffered only for conversion. When an upstream protocol requires SSE for a non-streaming caller, including a native OpenAI Responses call routed to an OpenAI subscription Endpoint, Yabane accumulates only normalized output state and returns one non-streaming response in the caller's protocol; a truncated upstream stream returns `502` instead of a partial success, and an upstream protocol-level failure remains a failure event or `502` after conversion.
* Proxying strips standard hop-by-hop headers, caller cookies, and upstream `Set-Cookie` headers while preserving other end-to-end upstream headers, status codes, and body bytes; this prevents same-origin administrator sessions from reaching an upstream or being overwritten by one. Cross-protocol forwarding additionally removes caller-supplied `OpenAI-Organization`, `OpenAI-Project`, `anthropic-version`, and `anthropic-beta` context before applying explicit Provider/Endpoint headers and target-protocol defaults, requests an identity-encoded upstream body, and removes stale content encoding, range, digest, and entity validator headers after transforming a response.
* Multiple inference requests can execute concurrently and reuse pooled upstream connections.
* Every failed request that reaches upstream forwarding is recorded in Activity with routing metadata, available timing, and a structured safe failure stage, category, and administrator-facing message: connection/transport errors, upstream HTTP errors, interrupted or protocol-failed streams, response-read errors, and protocol-conversion errors are distinguished without persisting proxy addresses, upstream URLs, credentials, prompts, responses, or untrusted upstream error text. Activity request details explain configured SOCKS5 connection failures and recommend proxy-side hostname resolution when `socks5` and `socks5h` differ. Transport failures return a safe actionable `502` message, while server logs at the normal error level include the request ID, proxy-use flag, and the same safe failure stage, category, and message without requiring temporary debug instrumentation.
* Request bodies larger than 32 MiB are rejected.

## Upstream endpoints and keys

* An Endpoint explicitly declares Anthropic Messages, OpenAI Chat Completions only, OpenAI Responses only, OpenAI subscription Responses, or legacy OpenAI-compatible dual-surface behavior; existing `openai_compatible` configurations retain their Chat-and-Responses behavior, while the single-surface types make cross-protocol routing deterministic without model-name inference.
* A provider can contain multiple API endpoints, and the admin console can add, edit, or delete endpoints after provider creation; editing standard Endpoints supports API type, base URL, SOCKS5 proxy, and whether credentials are required without exposing or replacing existing secrets or Endpoint request defaults, removes route credential references atomically when authentication is disabled, and rejects enabling required authentication while a keyless route still targets the Endpoint, while fixed OpenAI subscription Endpoints allow only their SOCKS5 proxy to be edited and can be deleted and reconnected but not converted in place.
* An administrator can connect a ChatGPT Plus or Pro subscription as either a new Provider or an Endpoint on an existing Provider through OpenAI's device-code OAuth page; Yabane never receives the account password.
* OpenAI subscription access and refresh tokens and ChatGPT account ID are persisted only in the private Provider configuration, omitted from every management API response, refreshed before expiry under a per-Endpoint lock, and never accepted from or exposed to gateway callers; a refresh that began against an older credential cannot overwrite an Endpoint reconnected while it was in flight. The console presents automatic renewal as the primary credential state rather than implying that the current access token's expiry disconnects the account; its expandable technical detail identifies the timestamp as the current access token's validity and explains that an elapsed token is renewed on the next request.
* Each OpenAI device sign-in flow permits only one upstream poll at a time, and the console ignores and aborts stale polling when a newer flow starts or its dialog closes.
* OpenAI subscription inference always maps `POST /v1/responses` to the Extension-owned fixed URL `https://chatgpt.com/backend-api/codex/responses`, ignoring any stale or tampered persisted base URL, and follows pi-ai's authorized ChatGPT Codex HTTP behavior: it replaces caller authentication and Codex routing headers, injects the connected account ID and OAuth bearer token, identifies every request through this Endpoint as the pi integration with `originator: pi` and pi-ai's platform-shaped `User-Agent` regardless of the gateway caller, requests identity-encoded SSE for transparent usage observation, supplies the missing `text/event-stream` response type when the Codex backend omits it, and sends `OpenAI-Beta: responses=experimental`; when a non-empty valid `prompt_cache_key` is present, its first 64 Unicode characters also become the Core-managed `session-id` and `x-client-request-id` headers, while caller-supplied identity and affinity headers are never trusted. Other Endpoint types retain their normal header behavior.
* Endpoint IDs are immutable after creation because discovery metadata, model preferences, routes, credentials, and Activity all reference them; both initial Provider setup and later Endpoint creation show the Endpoint ID, prefill a unique API-type-based suggestion, and allow it to be customized before creation, while the edit dialog presents the ID with the same explicit Permanent badge, lock treatment, non-editable styling, and dependency explanation used for an immutable Provider ID.
* Changing or adding an Endpoint clears model availability and preferences tied to that Endpoint before persisting when applicable, then starts one background discovery refresh; the console does not issue a duplicate refresh.
* Deleting a Provider or Endpoint also removes every model-route target referring to that exact resource; routes left without targets are removed, and Endpoint deletion additionally removes its discovered-model availability and preferences.
* Model discovery records which endpoint exposes each model.
* A request for `provider/model` is sent to an endpoint that reported that model, hiding endpoint topology from the caller.
* Models unique to different endpoints of one provider remain externally accessible through the same provider prefix.
* If multiple compatible endpoints report the same model, the first configured matching endpoint is the visible automatic default.
* An administrator can configure one preferred Endpoint for a discovered model and protocol within a Provider; inference uses that preference before the first-compatible-endpoint default, while explicit public model routes remain higher priority.
* Stale model Endpoint preferences are removed when discovery no longer reports the model on that compatible Endpoint, and deleting an Endpoint removes its preferences.
* An explicit model route can select a compatible endpoint different from the first endpoint.
* Endpoint base URLs identify a shared API root; configuration rejects operation-specific URLs ending in `/chat/completions`, `/responses`, `/messages`, or `/models`, while nested roots such as OpenCode Go’s `/zen/go/v1` remain valid for model discovery and inference.
* Each endpoint can optionally route model discovery and inference traffic through a `socks5://` or `socks5h://` proxy; OpenAI subscription Endpoints also use that proxy for device-code OAuth polling, token exchange, and token refresh.
* SOCKS5 proxy settings using another URL scheme are rejected with `400`.
* An endpoint can require an upstream API key or operate without one.
* An endpoint requiring a key cannot proxy when it has no enabled positive-weight key.
* An endpoint can contain multiple independently enabled upstream API keys.
* Default upstream key selection performs deterministic weighted round robin across enabled positive-weight keys.
* Disabled upstream keys receive no default traffic; an upstream key referenced by any retained model-route target, including a temporarily disabled target, cannot be disabled until those references are updated or deleted.
* OpenAI-compatible upstream credentials are sent as `Authorization: Bearer <key>`.
* Anthropic upstream credentials are sent as `x-api-key: <key>`.
* The caller's authorization headers and cookies are never forwarded to the upstream provider.

## Model-specific routing

* A model route creates a public model alias that clients call without a `provider/` prefix.
* A route target explicitly maps that public pattern to an upstream provider, endpoint, credential (an API key or connected subscription), and the exact model ID understood by that upstream; the upstream model does not include Yabane’s Provider prefix, though native namespaced IDs such as `google/model-name` remain valid.
* The route editor defaults to the simple alias task with only destination and upstream model fields, explains upstream model IDs, offers models discovered from the selected Endpoint as optional input suggestions, clearly permits custom IDs that were not discovered, and rejects an accidentally repeated Yabane Provider prefix while preserving legitimate native namespaced model IDs.
* Multi-destination traffic splitting is progressively disclosed behind an explicit action; only then does the editor show exact per-target percentage shares, require all shares to total 100%, and allow destinations to be added or removed while retaining at least one; adding, removing, turning on, or turning off a destination redistributes traffic evenly across destinations with positive shares instead of repeatedly normalizing stale values.
* Existing model routes can be opened in the route editor, including all weighted destinations, and saved with either the original or a changed public model pattern.
* A model route can retain targets with a 0% share as inactive destinations; setting a share to 0% or turning its Traffic switch off are equivalent, at least one target must have a positive share, and weighted round robin uses only positive-share targets so operators can switch traffic without deleting destinations.
* A model route can be an exact model ID or one trailing prefix wildcard.
* Exact model routes take precedence over wildcard routes.
* The longest matching wildcard prefix takes precedence over shorter prefixes.
* If no model route matches, each selected Endpoint uses its default credential behavior: weighted key selection for key-based Endpoints or the connected OAuth credential for an OpenAI subscription Endpoint.
* A model route explicitly selects an Endpoint and its applicable credential: key-based targets select one enabled upstream API key, OpenAI subscription targets use the Endpoint's connected OAuth subscription, and Endpoints configured without authentication use no credential; subscription and unauthenticated targets reject a non-empty API-key ID instead of silently ignoring it.
* Upstream-key update and deletion URLs include both Provider and Endpoint identity because key IDs are unique only within an Endpoint.
* The Provider detail console can delete each upstream key from within its owning Endpoint.
* Deleting an upstream key removes global-route targets referring to that exact Provider, Endpoint, and key; a route with no remaining targets is removed.

## Model discovery

* Creating a provider automatically starts model discovery without blocking provider creation.
* An administrator can explicitly refresh models for one provider or all providers.
* The console distinguishes discovery not yet run, successful empty results, and discovery failures.
* Provider details summarize the model catalog with unique-model count, shared-model count, configured Endpoint-default count, per-Endpoint coverage, discovery freshness, and a bounded searchable catalog instead of presenting an empty count-only card.
* The model catalog keeps Endpoint coverage below the primary model totals, and its expanded browser uses a full-width working surface; it displays each model’s Endpoint availability and effective default routing, provides working search, clear, and complete Previous/Next pagination over all matches, and lets shared models be managed in a searchable bounded preference editor without rendering the full collection by default.
* Large provider model collections are collapsed by default and can be searched in a bounded model browser instead of rendering an unbounded wall of model labels.
* Successful model discovery and the latest discovery status are persisted for the admin console; results are discarded if their Provider Endpoint or credential inputs changed while discovery was in flight, and a persistence failure leaves the in-memory catalog unchanged.
* The bundled OpenAI Subscription Extension owns Yabane's explicit pi-ai-aligned ChatGPT Codex model catalog rather than calling an unsupported upstream `/models` operation; it also owns device authorization and token refresh network behavior plus Codex-specific target path, request body, identity Header, affinity Header, and streaming-response requirements, while the existing Provider and Endpoint console and management API entry points remain unchanged.
* `GET /v1/models` returns an OpenAI-compatible list envelope.
* Model discovery concurrently queries configured provider endpoints and enabled upstream keys.
* OpenAI-compatible discovery accepts both `{ "data": [...] }` and a top-level model array; nested OpenAI-compatible API roots such as `https://opencode.ai/zen/go/v1` resolve discovery at that root’s `/models` resource.
* Anthropic discovery uses the Anthropic authentication and version headers.
* Models are merged across endpoints, deduplicated by ID, and sorted while retaining endpoint availability metadata for internal routing.
* Returned model IDs use the `provider/model` form without duplicating an existing provider prefix.
* Failure to discover models from one provider does not hide successfully discovered models from other providers.
* Discovered models are reference data and do not create locally managed model definitions.

## Activity and statistics

* Each completed proxied response records request timestamp, request ID, API path, public model, provider, endpoint, caller protocol, upstream protocol, final semantic status, total latency, gateway preparation time, time until upstream response headers, time to first response-body byte when observed, generation time after that first byte, streaming flag, available usage totals, and upstream-reported cost when present; Activity never retains prompts or response content, while its detail dialog may link by request ID to content separately retained by the Traffic Capture Extension. A cross-protocol conversion failure is recorded as `502`, including SSE failures discovered after HTTP response headers have already been sent, so Activity success statistics reflect the completed stream rather than only the upstream's initial HTTP status.
* Upstream cost is read from `usage.cost`, `usage.total_cost`, or `response.usage.cost` in OpenAI and Anthropic responses, including SSE usage events; requests without upstream cost record `null`, which the console displays as `—` or `$0.00` rather than fabricating a value.
* Activity statistics aggregate reported cost alongside request and token totals, and the console shows cost in the Overview metric, chart tooltips, and Request explorer rows.
* OpenAI Chat Completions and Responses usage and Anthropic Messages usage are normalized to input, output, and cached token counters when upstream reports them.
* SSE usage parsing honors event framing across arbitrary network chunks, supports CRLF and multiline data fields, ignores comments and `[DONE]`, reads OpenAI Responses usage nested under `response`, and combines Anthropic usage split across `message_start` and `message_delta` events.
* Activity statistics aggregate exact request, token, success, streaming, latency, and reported-cost totals over a caller-selected time range, optionally filter them by Provider, and return server-side time buckets plus ranked Provider and model dimensions; Overview totals and charts do not silently truncate to the newest 1,000 Request explorer records.
* The Activity Overview presents request, total-token, cache-hit, success-rate, streaming, average-latency, and reported-cost summaries with sparklines; its time-bucketed timeline can switch among requests, tokens, and latency and lets pointer, keyboard, and touch users inspect each interval's volume, health, latency, cache, and cost before the ranked Provider and model breakdowns. Summary cards and timeline details use the available width on desktop, collapse progressively on tablet, and become swipeable or compact on phones without removing the underlying information.
* Activity can be filtered by time range and Provider, automatically refreshes statistics and requests at a bounded cadence while the page and browser tab are visible, can be refreshed on demand, and can be switched between the visual Overview and a searchable Request explorer with status filtering; Overview fetches only its small recent-request sample, while the explorer uses server-side search, status, Provider, and complete Previous/Next pagination over a stable refresh snapshot with at most 100 rows fetched and rendered at once; the explorer adapts its usable list height to the viewport, emphasizes model, route, status, latency, and token output while retaining secondary metadata, and selecting a request opens a responsive detail dialog with its route, protocol, status, timing breakdown, token usage, derived output throughput, and cost while reiterating that prompt and response content are not retained.
* Activity remains immediately queryable in memory and is batch-written after 10 records or 60 seconds rather than writing every request synchronously.
* Normal Activity flushes append JSON Lines instead of rewriting the full history; each periodic flush atomically compacts records older than the persisted retention policy, defaulting initially to 30 days, even when no new requests arrive.
* Pending Activity records are flushed when Yabane completes graceful shutdown.
* Activity data management uses a dedicated dialog rather than immediate Import/Export actions: export requires choosing a time range and previews record count, estimated size, and oldest/newest timestamps before download.
* An administrator can export retained Activity as a timestamp-named, versioned Yabane JSON file and import it into another instance without requiring matching Provider or Endpoint configuration; imported routing metadata remains visible as originally recorded.
* Before an Activity import writes anything, the console validates the selected file and previews its size plus total, new, already-present, and outside-retention record counts; invalid files remain visibly rejected, and the completed import reports its final outcome in the same dialog.
* Every installation persists a random Activity instance ID; Activity import is idempotent by source instance ID plus request ID, so repeated and transitive imports are skipped without treating coincident request IDs from different instances as the same record. Records outside the destination retention window are reported and skipped, accepted records are atomically persisted, and preview and import results report imported, duplicate, expired, and total counts.
* Activity retention defaults to 30 days or a valid initial `YABANE_ACTIVITY_RETENTION_DAYS` value from 1 to 3650, can be changed and persisted from the console, and continuously compacts both memory and `data/activity.jsonl`; invalid initial values fail startup visibly, and reducing retention immediately excludes and removes expired records.

## Admin data safety

* Admin provider responses never expose upstream API-key secrets.
* Authenticated admin gateway API-key list responses expose generated secrets for reveal/copy but never expose secret hashes.
* Technical identifiers, URLs, credentials, and model patterns use monospace presentation in the console.
