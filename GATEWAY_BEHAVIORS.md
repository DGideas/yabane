# Yabane Gateway Behavior Checklist

This file is the source checklist for end-to-end gateway behavior. Each entry is one externally observable rule with a stable ID (`SVC-01`, `PROXY-07`, …) so a commit, a test, or a review comment can name the exact behavior it covers. Entries say what an administrator or caller observes, not how the process implements it; internal mechanisms belong in the code and its unit tests.

## Service and administration

* **SVC-01** Yabane loads local environment configuration from `.env` when present while preserving variables already supplied by the process environment.
* **SVC-02** `yabane --help` and `yabane --version` print help or Git commit/time build information and exit without loading configuration or starting the server; unknown or malformed arguments fail visibly, and Yabane presents no application version anywhere.
* **SVC-03** Yabane listens on the address passed through `--addr`, defaulting to `127.0.0.1:8080`; the listen address is intentionally not configurable through an environment variable.
* **SVC-04** `GET /healthz` returns `200` and does not require a gateway API key.
* **SVC-05** The web admin console uses a separate administrator session and never accepts gateway API keys as admin authentication.
* **SVC-06** On first use, the console requires creation of the single administrator with username, email, and a password of at least eight characters, and concurrent setup attempts cannot persist a second administrator.
* **SVC-07** Administrator passwords are persisted only as Argon2 password hashes.
* **SVC-08** Successful setup or login creates an HttpOnly, SameSite=Strict session cookie with a 24-hour server-enforced lifetime; logout revokes the current session and an expired session no longer authenticates.
* **SVC-09** Protected `/admin/*` APIs return `401` without a valid administrator session, while session, setup, login, static resources, and health remain public.
* **SVC-10** Initial administrator setup does not require a CAPTCHA.
* **SVC-11** Login requires a Cloudflare Turnstile token only when both a secret and a matching site key are available; the backend validates success, the `login` action, and an allowed hostname with Siteverify, and an unconfigured or incomplete Turnstile configuration disables CAPTCHA.
* **SVC-12** When the always-pass Turnstile test secret is configured and no site key is specified, the console uses Cloudflare's matching test site key so local login works without a production widget.
* **SVC-13** Unauthenticated visitors see a login screen that accepts username or email plus password, with initial focus in the username-or-email field; first-use administrator registration uses the same form.
* **SVC-14** The top-right account menu shows the signed-in username and email with explicit Manage profile and Sign out actions.
* **SVC-15** An administrator can update username, email, and password; changing the password additionally requires the correct current password and a new password of at least eight characters, and Gateway API keys cannot modify the administrator profile.
* **SVC-16** The console exposes the Yabane Git commit, commit time, and bundled MIT license information, and links to the project GitHub repository.
* **SVC-17** The embedded API reference at `/docs` renders the bundled OpenAPI specification served at `/openapi.json` and can execute requests against the running instance using the browser session or a pasted Bearer key; its prose names the Provider side instead of using the direction-relative word "upstream".
* **SVC-18** API Access and each Provider detail page expose the getting-started guide, which groups Pi, OpenCode, Claude Code, Codex, and VS Code Copilot guidance behind an Agent selector while offering selector-free Generic Agent values plus Shell and test-request tabs.
* **SVC-19** The guide uses current Gateway URLs, discovered `provider/model` IDs, public route aliases, and Gateway API keys to generate copyable setup instructions without exposing upstream credentials, explicitly marks VS Code Copilot as unsupported for arbitrary custom base URLs unless an extension provides that capability, and explains Yabane's explicit cross-protocol conversion behavior; API Access also shows a copyable `GET /v1/models` example that uses the current console origin and runs as a single shell command.
* **SVC-20** Opened from a Provider page, the guide defaults to a model discovered from that Provider and, when one exists, a non-expired Gateway API key authorized for it.
* **SVC-21** Provider, gateway authentication, administrator, model-route, and per-Extension enabled-state configuration is persisted under `data/` and restored after restart.
* **SVC-22** A configuration change is published as one unit: an interrupted update never exposes partial JSON, and a malformed, unsupported, or non-configuration-path recovery record fails startup visibly instead of being replayed.
* **SVC-23** Missing configuration files produce empty or default configuration.
* **SVC-24** Malformed or unreadable configuration fails startup visibly instead of silently overwriting or ambiguously addressing resources; this includes duplicate Provider, Endpoint, key, Gateway API-key, Management API-key, or model-route identities, model routes with no targets, invalid Provider model IDs, and traffic shares that do not total 100%; every deletion that removes a route destination redistributes the surviving shares so the file this instance writes still totals 100%, and a route left without a usable destination is removed.
* **SVC-25** Startup also rejects dangling references — Provider Request Defaults scopes, discovered-model Endpoint availability and preferences, Gateway API-key Provider scopes, and model-route Provider, Endpoint, or credential references — rather than loading mutually inconsistent files.
* **SVC-26** `YABANE_LOG` controls logging, defaults to `info`, and an invalid filter fails startup.
* **SVC-27** The Providers page lists providers with `provider/model-id` examples and a per-Provider request sparkline summarizing the last 24 hours.
* **SVC-28** A Provider's display name can be edited after creation without replacing omitted Provider settings, while its Provider ID stays immutable because Gateway API-key scopes, model routes, request URLs, and Activity reference it; the edit dialog states that boundary explicitly instead of implying that deletion is the only Provider-level operation.
* **SVC-29** Provider details present upstream API keys inside their owning Endpoint, and key-creation actions name and preselect that Endpoint so Provider, Endpoint, and key actions are not presented as peers.
* **SVC-30** Upstream-key traffic distribution is presented as percentages that must total 100% across enabled keys; a newly added key uses the standard default weight.
* **SVC-31** Settings search finds top-level settings, provider-model discovery, gateway-key generation, every Extension compiled into the current binary, and configured providers, and navigates to the selected result; Extension entries come from the runtime catalog so the search cannot list a stale or removed extension.
* **SVC-32** The Extensions page lists the trusted native Rust extensions compiled into the current binary with their enabled state, versions, Extension API versions, declared Hook stages spelled in Provider terms such as `Provider request` and `Provider exchange` while the Extension API keeps its stable Hook IDs, and implementation type, without implying that arbitrary runtime code can be installed.
* **SVC-33** An administrator can persistently enable or disable each compiled Extension without deleting its configuration, including an Endpoint implementation that already has configured Endpoints, and before disabling the OpenAI Subscription Extension with configured Endpoints the console warns that those resources and their routing, discovery, OAuth, refresh, and inference behavior remain unavailable until it is re-enabled.
* **SVC-34** The Extensions page links to the public Extension development guide and shows copyable default-build, runtime `--no-extensions`, and Core-only build commands even when no Extension is included.
* **SVC-35** `--no-extensions` disables all compiled Extension Hooks for that process without changing their persisted enabled states; the API and console still list the compiled implementations, identify the startup override, and do not allow runtime enablement until Yabane restarts without the option.
* **SVC-36** Gateway API keys authenticate inference requests and model listing within their provider scopes, while Management API keys authenticate the control API; administrator profile and Management-key endpoints require a browser session.
* **SVC-37** Each administrator can create named Management API keys beginning with `yab_mgmt_` and an optional expiry; the secret is shown once, only its hash is persisted and compared in constant time, last-use times are tracked and published only after successful persistence, and revocation is immediate.
* **SVC-38** The authenticated Home page visualizes the last 24 hours of request and token usage, links to Activity and configured providers, and refreshes its statistics automatically while the page and browser tab are visible.
* **SVC-39** The Request flow chart preserves the 24-hour total while adapting to its own available width, progressively combining half-hour intervals into readable hourly or two-hour bars on narrower layouts; every bar keeps the same rendered width and stays centered on its interval even when its column carries an axis label wider than the column.
* **SVC-40** The bundled Traffic Capture Extension is stopped by default and provides an explicit Provider- and Endpoint-scoped capture of the next 1 to 100 matching requests within a fixed capture window that matching traffic does not extend, with bounded bodies, additional header redaction, and 1-to-30-day retention; capture requires an enabled Extension and a future expiry.
* **SVC-41** The Traffic Capture console summarizes the exact scope before activation and locks the scope controls while a session is active, lets captures be inspected, manually refreshed, or deleted, and warns that prompts, files, tools, and model output may be sensitive and that truncating a stream can prevent assembly.
* **SVC-42** Traffic Capture stores bounded request and response bodies outside Activity, always redacts Core-managed credentials, and reports failures and truncation explicitly; a failed persistence is reported as a dropped capture instead of being presented as stored, and captures are opened from their owning Extension console rather than from Activity.
* **SVC-43** A complete captured SSE exchange can be assembled into the corresponding non-streaming protocol response while the exact raw-wire view remains available; a truncated, malformed, or unterminated capture is visibly unavailable for assembly instead of being presented as complete.
* **SVC-44** An active capture session must be stopped before the Extension is disabled or its scoped Provider or Endpoint is deleted; deleting a resource clears an inactive matching scope, so saved capture configuration never becomes silently inert or orphaned.
* **SVC-45** The built-in Request Defaults extension applies Provider-level extra headers and JSON request-body fields to every current and future endpoint of that Provider or to an explicit non-empty selection, and endpoint-level values override matching Provider-level values where the Provider defaults apply.
* **SVC-46** The Provider page identifies Request Defaults as an extension-provided request modification with its enabled or disabled state, offers all-endpoint and selected-endpoint scope controls, and validates endpoint selection, duplicate names, HTTP header syntax, reserved authentication and hop-by-hop headers, and each body field's JSON value before saving; a disabled scope visibly warns that saved values are not applied to upstream requests, and an unavailable extension disables configuration and links to build instructions.
* **SVC-47** The Model pricing page centrally lists and edits explicit Global, Provider, and Endpoint rules without requiring navigation into a Provider; global prices are stored in `data/pricing.json` while Provider and Endpoint prices in `data/providers.json` remain valid overrides.
* **SVC-48** Every pricing rule states which of a request's two model names it prices: the outgoing model Yabane sends to the Provider after route rewriting, or the incoming model name the caller sends, including a public route alias; incoming-name prices are Global-only, and no pattern may be saved as both names in one table; the editor asks which model name a price matches before where the rule applies, states that the outgoing model is not the caller's model or a route alias while never using the direction-relative word `upstream`, and forces Global scope with the reason visible when the caller's name is chosen.
* **SVC-49** Within one scope and one name an exact pattern wins; otherwise one trailing `*` performs prefix matching and the longest matching prefix wins, using the same pattern semantics as Model routing.
* **SVC-50** Rates resolve field by field with outgoing rules first — Endpoint, Provider, and Global outgoing rules win the fields they define and a Global incoming rule fills the rest — so one price covers every destination of an alias.
* **SVC-51** Pricing suggestions may come from saved pricing, Model Router destinations, Provider discovery, and historical Activity, but remain autocomplete only: any valid exact or trailing-wildcard pattern can be entered and Yabane has no built-in model or price catalog.
* **SVC-52** On desktop layouts with enough horizontal space the pricing editor can fetch matching public price references from the CORS-enabled `https://models.dev/api.json` catalog after the administrator enters at least two model characters; the browser sends no Yabane or Provider credentials, rates enter the form only through an explicit `Use rates` action, and Yabane neither persists the catalog nor treats it as an implicit price source, while narrow layouts omit the panel.
* **SVC-53** Provider and Endpoint pricing rules are owned by their resource: deleting an Endpoint deletes its pricing table, deleting a Provider deletes its own table and every child Endpoint table, and Global patterns remain unchanged by those deletions.
* **SVC-54** Global, Provider, and Endpoint settings define explicit input, output, and cache-read USD rates per million tokens; the persisted schema retains a reserved cache-write rate for compatibility, but the console does not offer it and estimation does not apply it because normalized usage has no cache-write token count.
* **SVC-55** Invalid or negative rates, patterns other than an exact ID or one non-empty trailing `*`, patterns padded with whitespace that could never match, and incoming-name prices in Provider or Endpoint tables are rejected, and clearing both model maps removes that pricing scope.
* **SVC-56** Saved pricing tables carry a server-assigned Unix `updated_at` timestamp rather than a client-controlled or incrementing version.
* **SVC-57** Saving or editing rates affects future Activity automatically; an explicit Activity cost refresh recalculates every non-reported record — including existing `estimated` values and records with `cost: null` — from the current pricing snapshot, never changes `reported` values, and leaves an existing estimate unchanged when no current pricing matches.
* **SVC-58** No Provider type, Endpoint URL, or model name supplies an implicit price: OpenAI subscription and Qwen Token Plan rates must be configured explicitly and remain usage-value estimates rather than subscription billing.

## Gateway authentication

* **AUTH-01** Gateway API-key authentication is enabled by default.
* **AUTH-02** An administrator can enable or disable gateway API-key authentication globally.
* **AUTH-03** When authentication is disabled, `/v1/*` requests do not require an `Authorization` header.
* **AUTH-04** When authentication is enabled, a request to `/v1/*` with a missing, malformed, unknown, deleted, or expired gateway API key returns `401`.
* **AUTH-05** A valid non-expired gateway API key authorizes requests within its provider scope, and inference routing and model listing use the scope established by authentication rather than re-reading caller credentials.
* **AUTH-06** A gateway API key with an empty provider scope can access every configured provider, and the console states that an empty selection means unrestricted access.
* **AUTH-07** A provider-scoped gateway API key receives `403` when an inference request selects a provider outside its scope.
* **AUTH-08** `GET /v1/models` returns only models belonging to providers allowed by the gateway API key.
* **AUTH-09** Generated gateway API keys begin with `sk-` and use cryptographically secure random bytes.
* **AUTH-10** A generated gateway API-key secret is returned by the create operation and remains available to authenticated administrators in later list operations; the list identifies an existing key by a short masked prefix rather than displaying or embedding the full secret, and the stored SHA-256 hash is compared in constant time for request authentication.
* **AUTH-11** The generated-key dialog and the API-key list provide Copy API key actions.
* **AUTH-12** Gateway API keys support an optional note, optional expiration time, and optional provider allowlist, and administrators can patch any subset of those fields without resetting omitted values or changing the secret; the console visibly marks expired keys, and creating or updating a scoped key is serialized with Provider deletion so a concurrently removed Provider cannot leave a dangling allowlist reference.
* **AUTH-13** Creating or editing a gateway API key with an expiration time in the past is rejected with `400`; an expired key can be reactivated only by editing it to have no expiry or a future expiry.
* **AUTH-14** Creating or editing a gateway API key with an unknown provider in its allowlist is rejected with `400`.
* **AUTH-15** Deleting a gateway API key revokes it immediately.

## Provider routing and proxying

* **PROXY-01** Inference requests select a provider from the `provider/model` request model ID.
* **PROXY-02** Only the first model path segment is removed; the remaining namespaced upstream model ID is preserved exactly, so native upstream namespaces such as `google/model-name` survive.
* **PROXY-03** A model without a provider prefix, or with an unknown provider prefix, is rejected with `400`.
* **PROXY-04** A provider with no Endpoint exposing the requested model is rejected with `400`; while model discovery has not established Endpoint availability, any configured Endpoint remains eligible.
* **PROXY-05** Routing first chooses an available Endpoint native to the caller's API surface, then deterministically falls back to another available Endpoint exposing the same model through Yabane's explicit cross-protocol adapter; an Endpoint whose Extension is disabled is unavailable to automatic routing, so another eligible Endpoint may serve the model.
* **PROXY-06** An explicit model-route target always takes precedence over automatic selection, and fails visibly when its required Extension is disabled.
* **PROXY-07** The three protocol surfaces stay independent and path-bound: OpenAI Chat Completions is accepted only at `POST /v1/chat/completions`, OpenAI Responses only at `POST /v1/responses`, and Anthropic Messages only at `POST /v1/messages`.
* **PROXY-08** On a native protocol path, request fields other than the provider prefix in `model` are forwarded without semantic rewriting unless an explicitly configured request extension modifies them.
* **PROXY-09** Cross-protocol behavior happens only when the caller explicitly selects a non-native API surface; such requests map shared message roles, text, image, and document/file content, system instructions, function tools, tool choice, tool calls and results, output limits, supported stop sequences and sampling controls, streaming intent, structured-output formats, and usage fields.
* **PROXY-10** Anthropic cache-read input is additive to its `input_tokens`, so conversion normalizes it into the inclusive OpenAI input total while preserving it as the cached subset, and conversion back to Anthropic removes that subset from `input_tokens`.
* **PROXY-11** Document sources preserve their URL, data, file ID, and filename in the target wire shape, while known source-protocol fields and built-in tools with no target-protocol equivalent are not forwarded, invented, or inferred.
* **PROXY-12** OpenAI subscription Endpoints accept all three caller surfaces through the explicit adapter while their upstream connection remains streaming OpenAI Responses.
* **PROXY-13** Subscription inference always maps `POST /v1/responses` to the Extension-owned fixed URL `https://chatgpt.com/backend-api/codex/responses`, ignoring any stale or tampered persisted base URL.
* **PROXY-14** Subscription inference follows pi-ai's authorized Codex HTTP behavior: it replaces caller authentication and Codex routing headers, injects the connected account ID and OAuth bearer token, identifies every request through this Endpoint as the pi integration with `originator: pi` and pi-ai's platform-shaped `User-Agent`, supplies the missing `text/event-stream` response type when the Codex backend omits it, sends `OpenAI-Beta: responses=experimental`, and requests identity-encoded SSE for transparent usage observation.
* **PROXY-15** A subscription Endpoint re-derives identity and affinity from the request body and the connected subscription instead of trusting the caller: inbound `Content-Encoding`, `User-Agent`, `session-id`, and `x-client-request-id` values are replaced, and every `cf-*`, `x-forwarded-*`, `cdn-loop`, `forwarded`, and `via` header is dropped regardless of casing because the Codex backend rejects requests carrying reverse-proxy metadata; a non-empty valid `prompt_cache_key` also becomes the Extension-owned `session-id` and `x-client-request-id` headers using its first 64 Unicode characters.
* **PROXY-16** Caller headers carrying no proxy metadata are still forwarded untouched to a subscription Endpoint, and other Endpoint types keep their normal header behavior and receive caller headers unchanged.
* **PROXY-17** Subscription inference requires streaming upstream and rewrites the public Responses body to pi-ai's Codex shape: it forces `stream: true` and `store: false`, includes `reasoning.encrypted_content`, applies defaults for missing instructions, text verbosity, tool choice, and parallel tool calls, moves a leading string-content `developer` or `system` input into `instructions`, converts the standard Responses string-input shorthand to its equivalent user-message form, and omits the unsupported public `max_output_tokens` field.
* **PROXY-18** The versioned native Extension API v1 lets compiled Extensions register Provider-specific Endpoint metadata, models, subscription OAuth lifecycle, and final wire preparation while Core retains resource routing, persistence, credential ownership, and redaction.
* **PROXY-19** Extension API v1 provides ordered upstream-request and upstream-header Hook chains: each Hook sees earlier modifications, and a structured rejection, invalid result, failure, or panic is attributed to its extension instance, stops later Hooks, and prevents the upstream request without exposing the internal error to the caller.
* **PROXY-20** Extension API v1 also provides read-only upstream-exchange observers over final request data, response headers, streaming chunks, and the completion outcome; observer failure never changes the proxied result, and a build or runtime configuration with no enabled Hooks preserves the normal proxy path.
* **PROXY-21** Core irreversibly redacts upstream authentication, API keys, cookies, subscription identity, proxy authentication, and request-affinity header values before making an exchange available to an Extension, and captures credential-redacted snapshots only for observers whose preflight declares interest.
* **PROXY-22** Extension header Hooks receive the final upstream header map after Core sanitizes caller-supplied headers but before Core injects upstream authentication, so a Hook may add, override, or remove any non-reserved header; inserting, changing, or removing a reserved authentication, cookie, subscription-identity, or hop-by-hop header is rejected and attributed to the offending extension instance.
* **PROXY-23** Upstream status codes and error response bodies are visible to the caller, including non-SSE JSON errors returned by an Endpoint that otherwise requires successful responses to stream.
* **PROXY-24** Successful cross-protocol responses use the caller's selected response envelope and carry `x-yabane-protocol-conversion` naming the upstream-to-caller conversion.
* **PROXY-25** Every response produced by the proxy handler carries `x-yabane-request-id`, matching the `request_id` of the Activity record for the same request, including requests rejected before an upstream was selected.
* **PROXY-26** Failed responses additionally carry `x-yabane-error-origin`: `upstream` when the body is the provider's own error bytes verbatim, and `yabane` when Yabane authored the message, which covers failures raised before an upstream was reached, messages written by a compiled Extension, and upstream conditions Yabane had to re-render as its own `502`.
* **PROXY-27** The origin header names the author of the message, not responsibility for the failure: a successful response carries no origin, a failure first visible inside a body Yabane streams through unbuffered carries none, and a response produced outside the proxy handler — such as gateway API-key rejection — carries neither header.
* **PROXY-28** Native-protocol response bodies, including SSE, are streamed without full response buffering; cross-protocol SSE is converted incrementally, retaining completed output only when a non-streaming caller or the target Responses terminal event requires it, and an individual unterminated SSE frame larger than 8 MiB is rejected.
* **PROXY-29** Cross-protocol non-streaming JSON responses are buffered only for conversion; when an upstream protocol requires SSE for a non-streaming caller — including a native OpenAI Responses call routed to an OpenAI subscription Endpoint — Yabane accumulates only normalized output state and returns one non-streaming response in the caller's protocol.
* **PROXY-30** A truncated upstream stream returns `502` instead of a partial success, and an upstream protocol-level failure remains a failure event or `502` after conversion.
* **PROXY-31** Proxying strips standard hop-by-hop headers, caller cookies, upstream `Set-Cookie` headers, and every upstream-supplied `x-yabane-*` header while preserving other end-to-end upstream headers, status codes, and body bytes, so same-origin administrator sessions cannot reach an upstream or be overwritten by one and the `x-yabane-*` response namespace stays owned by the gateway.
* **PROXY-32** Cross-protocol forwarding additionally removes caller-supplied `OpenAI-Organization`, `OpenAI-Project`, `anthropic-version`, and `anthropic-beta` context before applying explicit Provider and Endpoint headers and target-protocol defaults, requests an identity-encoded upstream body, and removes stale content-encoding, range, digest, and entity-validator headers after transforming a response.
* **PROXY-33** Core's caller-header sanitization is identical for every Endpoint type and never branches on an Endpoint's API type; a provider that must drop inbound headers before they reach its upstream owns that removal inside its own Extension, which is what keeps Core a transparent proxy.
* **PROXY-34** Inference upstream connections have process-wide connect, per-read, and total request deadlines, defaulting to 15 seconds, 300 seconds, and 28800 seconds (8 hours) and configurable from 1 through 86400 seconds with `YABANE_UPSTREAM_CONNECT_TIMEOUT_SECONDS`, `YABANE_UPSTREAM_READ_TIMEOUT_SECONDS`, and `YABANE_UPSTREAM_TOTAL_TIMEOUT_SECONDS`.
* **PROXY-35** Successful reads reset the per-read deadline while the total deadline still bounds an upstream that sends only keepalives, and the same deadlines apply to direct and SOCKS5 connections, while shorter operation-specific model-discovery and subscription-OAuth deadlines retain precedence.
* **PROXY-36** A timeout before response headers returns a safe `502`, a timeout after streaming starts terminates the stream, and both are recorded in Activity with a structured timeout failure.
* **PROXY-37** Multiple inference requests can execute concurrently and reuse pooled upstream connections.
* **PROXY-38** Every failed request that reaches upstream forwarding is recorded in Activity with routing metadata, available timing, and a structured safe failure stage, category, and administrator-facing message that distinguishes connection and transport errors, upstream HTTP errors, interrupted or protocol-failed streams, response-read errors, and protocol-conversion errors.
* **PROXY-39** Failure records never persist proxy addresses, upstream URLs, credentials, prompts, responses, or untrusted upstream error text, and the messages name the Provider side instead of using the direction-relative word "upstream"; the same wording reaches API callers and the console, and Activity request details explain configured SOCKS5 connection failures and recommend proxy-side hostname resolution when `socks5` and `socks5h` differ.
* **PROXY-40** Transport failures return a safe actionable `502` message, and server logs at the normal error level include the request ID, proxy-use flag, and the same safe failure stage, category, and message without requiring temporary debug instrumentation.
* **PROXY-41** Request bodies larger than 32 MiB are rejected.

## Upstream endpoints and keys

* **ENDPOINT-01** An Endpoint explicitly declares Anthropic Messages, OpenAI Chat Completions only, OpenAI Responses only, OpenAI subscription Responses, or legacy OpenAI-compatible dual-surface behavior; existing `openai_compatible` configurations retain their Chat-and-Responses behavior, while the single-surface types make cross-protocol routing deterministic without inferring capability from model names.
* **ENDPOINT-02** A provider can contain multiple API endpoints, and the admin console can add, edit, or delete endpoints after provider creation; creation forms ask for the Endpoint ID and API type before the conditional base URL, so fixed OpenAI subscription Endpoints never ask the administrator for a URL.
* **ENDPOINT-03** Editing a standard Endpoint supports API type, base URL, SOCKS5 proxy, and whether credentials are required, without exposing or replacing existing secrets or Endpoint request defaults.
* **ENDPOINT-04** Disabling required authentication removes route credential references atomically, and enabling it is rejected while a keyless route still targets the Endpoint; a fixed OpenAI subscription Endpoint allows only its SOCKS5 proxy to be edited and can be deleted and reconnected but not converted in place.
* **ENDPOINT-05** Endpoint IDs can be edited after creation and remain unique URL slugs within their Provider; renaming atomically updates discovered-model availability, model Endpoint preferences, explicit model-route destinations, Provider Request Defaults scope, and an inactive Traffic Capture scope while keeping upstream keys or the connected OAuth subscription attached, and an active Traffic Capture must be stopped first.
* **ENDPOINT-06** Historical Activity and retained captures remain immutable records of the Endpoint ID used when each request occurred, while initial Provider setup and later Endpoint creation prefill a unique API-type-based suggestion and the edit dialog explains that boundary.
* **ENDPOINT-07** Changing an Endpoint's connection settings or adding an Endpoint clears the model availability and preferences tied to that Endpoint before persisting when applicable, then starts one background discovery refresh; renaming alone preserves the catalog under the new ID and does not trigger discovery, and the console does not issue a duplicate refresh.
* **ENDPOINT-08** Deleting a Provider or Endpoint also removes every model-route target and inactive Traffic Capture scope referring to that exact resource, removes routes left without targets, and removes the Endpoint's discovered-model availability and preferences.
* **ENDPOINT-09** Provider deletion also removes that Provider from Gateway API-key allowlists, and a key scoped only to the deleted Provider is revoked rather than becoming unrestricted through the empty-allowlist meaning; the destructive confirmation summarizes affected child credentials, route destinations, and Gateway API keys, handles deletion failures visibly, and refreshes Provider, model-route, and gateway-authentication state after success.
* **ENDPOINT-10** An administrator can connect a ChatGPT Plus, Pro, or Business subscription as either a new Provider or an Endpoint on an existing Provider; device-code OAuth is the default, while browser OAuth is an explicit alternative for organizations that disable device sign-in.
* **ENDPOINT-11** Before browser OAuth can be launched the console explains that OpenAI's redirect to `localhost:1455` is expected to show a connection error or 404 and that the page is a successful intermediate step, then presents the complete copy-and-paste sequence.
* **ENDPOINT-12** Browser OAuth uses pi-ai's registered `http://localhost:1455/auth/callback`, asks the administrator to paste that complete callback URL once, strictly validates its origin, path, single code, and state, and performs the PKCE token exchange itself, so Yabane never receives the account password.
* **ENDPOINT-13** OpenAI subscription access and refresh tokens and the ChatGPT account ID are persisted only in the private Provider configuration, omitted from every management API response, refreshed before expiry under a per-Endpoint lock, and never accepted from or exposed to gateway callers; a refresh that began against an older credential cannot overwrite an Endpoint reconnected while it was in flight.
* **ENDPOINT-14** The console presents automatic renewal as the primary credential state rather than implying that the current access token's expiry disconnects the account, and its expandable technical detail identifies the timestamp as the current access token's validity and explains that an elapsed token is renewed on the next request.
* **ENDPOINT-15** Each OpenAI device sign-in flow permits only one upstream poll at a time and each browser OAuth flow only one completion exchange at a time; both expire after 15 minutes, and the console ignores and aborts stale polling when a newer flow starts or its dialog closes.
* **ENDPOINT-16** Model discovery records which endpoint exposes each model, a request for `provider/model` is sent to an endpoint that reported that model so endpoint topology stays hidden from the caller, and models unique to different endpoints of one provider remain externally accessible through the same provider prefix.
* **ENDPOINT-17** If multiple compatible endpoints report the same model, the first configured matching endpoint is the visible automatic default.
* **ENDPOINT-18** An administrator can configure one preferred Endpoint for a discovered model and protocol within a Provider; inference uses that preference before the first-compatible-endpoint default, while explicit public model routes remain higher priority.
* **ENDPOINT-19** Stale model Endpoint preferences are removed when discovery no longer reports the model on that compatible Endpoint, and deleting an Endpoint removes its preferences.
* **ENDPOINT-20** An explicit model route can select a compatible endpoint different from the first endpoint.
* **ENDPOINT-21** Endpoint base URLs identify a shared API root: configuration rejects operation-specific URLs ending in `/chat/completions`, `/responses`, `/messages`, or `/models`, while nested roots such as `/zen/go/v1` remain valid for model discovery and inference.
* **ENDPOINT-22** Each endpoint can optionally route model discovery and inference traffic through a `socks5://` or `socks5h://` proxy, which OpenAI subscription Endpoints also use for device-code OAuth polling, token exchange, and token refresh; SOCKS5 settings using another URL scheme are rejected with `400`.
* **ENDPOINT-23** An endpoint can require a Provider API key or operate without one, and an endpoint that requires a key cannot proxy while it has no enabled positive-weight key.
* **ENDPOINT-24** An endpoint can contain multiple independently enabled Provider API keys, and default key selection performs deterministic weighted round robin across the enabled positive-weight keys.
* **ENDPOINT-25** A Provider API key can be renamed after creation, and the rename keeps the key ID, secret, weight, enabled state, and every model-route reference intact so routing and discovery continue unchanged; a blank or whitespace-only name is rejected with `400`.
* **ENDPOINT-26** Disabled upstream keys receive no default traffic, and an upstream key referenced by any retained model-route target — including a temporarily disabled target — cannot be disabled until those references are updated or deleted.
* **ENDPOINT-27** OpenAI-compatible upstream credentials are sent as `Authorization: Bearer <key>` and Anthropic upstream credentials as `x-api-key: <key>`.
* **ENDPOINT-28** The caller's authorization headers and cookies are never forwarded to the upstream provider.
* **ENDPOINT-29** Each upstream key is managed inside its owning Endpoint in the console, and deleting a key removes the route targets referring to that exact Provider, Endpoint, and key, removing a route that has no remaining targets.

## Model-specific routing

* **ROUTE-01** A model route creates a public model alias that clients call without a `provider/` prefix.
* **ROUTE-02** A route target explicitly maps that public pattern to a Provider, Endpoint, credential (an API key or connected subscription), and the exact model ID understood by that upstream; the upstream model never includes Yabane's Provider prefix, though native namespaced IDs such as `google/model-name` remain valid.
* **ROUTE-03** A model route can be an exact model ID or one trailing prefix wildcard; exact routes beat wildcard routes, and the longest matching wildcard prefix beats shorter prefixes.
* **ROUTE-04** If no model route matches, each selected Endpoint uses its default credential behavior: weighted key selection for key-based Endpoints, the connected OAuth credential for an OpenAI subscription Endpoint, or no credential for an Endpoint that requires none.
* **ROUTE-05** A model route explicitly selects an Endpoint and its applicable credential: key-based targets select one enabled upstream API key, OpenAI subscription targets require the enabled OpenAI Subscription Extension and use the Endpoint's connected OAuth subscription, and Endpoints configured without authentication use no credential; subscription and unauthenticated targets reject a non-empty API-key ID instead of silently ignoring it.
* **ROUTE-06** Route validation and persistence are serialized with Provider and Endpoint mutations, so a concurrently removed resource cannot leave a dangling destination.
* **ROUTE-07** The route editor defaults to the simple alias task with only destination and Provider model fields, explains Provider model IDs, offers models discovered from the selected Endpoint as optional suggestions, permits custom IDs that were not discovered, and rejects an accidentally repeated Yabane Provider prefix while preserving legitimate native namespaced model IDs.
* **ROUTE-08** Multi-destination traffic splitting is progressively disclosed behind an explicit action; only then does the editor show exact per-target percentage shares, require them to total 100%, and keep at least one destination, while adding, removing, turning on, or turning off a destination redistributes traffic evenly across destinations with positive shares instead of repeatedly normalizing stale values.
* **ROUTE-09** A model route can retain targets with a 0% share as inactive destinations — a 0% share and a switched-off Traffic toggle are equivalent — and weighted round robin uses only positive-share targets, so operators can move traffic without deleting destinations.
* **ROUTE-10** Existing model routes can be opened in the route editor, including all weighted destinations, and saved with either the original or a changed public model pattern.
* **ROUTE-11** The Model routing page explains that rules bind matching models to a specific Endpoint and credential, shows exact and prefix examples, and makes clear that unmatched models retain default Endpoint credential selection, and keeps a long public model name inside its own row on a phone instead of letting the destination list scroll sideways.

## Model discovery

* **DISCOVERY-01** Creating a provider automatically starts model discovery without blocking provider creation, and an administrator can explicitly refresh models for one provider or all providers.
* **DISCOVERY-02** The console distinguishes discovery not yet run, successful empty results, and discovery failures.
* **DISCOVERY-03** Provider details summarize the model catalog with unique-model count, shared-model count, configured Endpoint-default count, per-Endpoint coverage, and discovery freshness.
* **DISCOVERY-04** The catalog browser shows each model's Endpoint availability and effective default routing, provides search, clear, and complete Previous/Next pagination over all matches, collapses large collections by default, and lets shared models be managed in a searchable bounded preference editor without rendering the full collection.
* **DISCOVERY-05** Successful model discovery and the latest discovery status are persisted for the admin console; a result is discarded if its Provider Endpoint or credential inputs changed while discovery was in flight, and a persistence failure leaves the in-memory catalog unchanged.
* **DISCOVERY-06** The bundled OpenAI Subscription Extension owns Yabane's explicit pi-ai-aligned ChatGPT Codex model catalog rather than calling an unsupported upstream `/models` operation, and also owns device authorization, token refresh, and the Codex-specific path, body, identity and affinity headers, proxy-metadata removal, and streaming requirements.
* **DISCOVERY-07** `GET /v1/models` returns an OpenAI-compatible list envelope from the persisted in-memory discovery cache without waiting for upstream Providers, and a failed or unavailable upstream refresh does not prevent callers from receiving the last successful catalog.
* **DISCOVERY-08** Model discovery concurrently queries configured provider endpoints and enabled upstream keys, and each upstream catalog request has a 10-second total timeout so an unresponsive Endpoint cannot indefinitely block an explicit refresh.
* **DISCOVERY-09** OpenAI-compatible discovery accepts both `{ "data": [...] }` and a top-level model array, and resolves nested OpenAI-compatible API roots such as `https://opencode.ai/zen/go/v1` at that root's `/models` resource.
* **DISCOVERY-10** Anthropic discovery uses the Anthropic authentication and version headers.
* **DISCOVERY-11** Models are merged across endpoints, deduplicated by ID, and sorted while retaining endpoint availability metadata for internal routing.
* **DISCOVERY-12** Returned model IDs use the `provider/model` form without duplicating an existing provider prefix.
* **DISCOVERY-13** Failure to discover models from one provider does not hide successfully discovered models from other providers.
* **DISCOVERY-14** Discovered models are reference data and do not create locally managed model definitions.

## Activity and statistics

* **ACTIVITY-01** Each completed proxied response records request timestamp, request ID, API path, the caller's exact requested model string, the exact final model ID sent upstream after explicitly configured request transformations, provider, endpoint, caller protocol, upstream protocol, final semantic status, the upstream protocol's finish reason or terminal status when reported, total latency, gateway preparation time, time until upstream response headers, time to first response-body byte when observed, generation time after that first byte, streaming flag, whether the Provider response itself streamed, available usage totals, cost, and whether that cost was upstream-reported or locally estimated.
* **ACTIVITY-02** The Activity request list labels the model received from the Client and the model sent to the Provider, replaces a duplicated identical value with an explicit `Same model ID` outcome, and its detail panel presents both exact values as `Client requested` and `Sent to Provider` with an explicit changed-or-unchanged result.
* **ACTIVITY-03** The detail panel groups `Client API` and `Provider API` with an explicit conversion outcome and places the selected `Provider` and `Endpoint` together under the routing destination, so weighted model-route and cross-protocol outcomes are explainable.
* **ACTIVITY-04** Older retained or imported records remain readable with unavailable upstream-model, finish-reason, and cost-source metadata.
* **ACTIVITY-05** Activity never retains prompts or response content, while its detail panel may link by request ID to content separately retained by the Traffic Capture Extension.
* **ACTIVITY-06** A cross-protocol conversion failure is recorded as `502`, including SSE failures discovered after HTTP response headers have already been sent, so Activity success statistics reflect the completed stream rather than only the upstream's initial HTTP status.
* **ACTIVITY-07** Provider-reported cost is read from `usage.cost`, `usage.total_cost`, or `response.usage.cost` in OpenAI and Anthropic responses, including SSE usage events, and always takes precedence.
* **ACTIVITY-08** When the Provider omits cost, Yabane estimates it only from explicitly configured matching patterns that have both input and output rates available field by field: an outgoing rule for the model ID the request carried to the Provider wins over a Global rule for the incoming model name the caller sent, narrower scopes win over broader ones, and cached input is removed from ordinary input and charged once at the configured cache-read rate or the input rate when no cache rate is supplied.
* **ACTIVITY-09** Each estimated record stores which scope, name, and pattern supplied each rate, so an estimate stays explainable after pricing changes; without Provider-reported cost or a complete matching explicit price, cost remains `null`.
* **ACTIVITY-10** A single-record cost refresh addresses the stable source-instance-plus-request-ID identity, so imported records with coincident request IDs cannot modify one another.
* **ACTIVITY-11** A cost refresh preserves upstream `reported` costs, recalculates existing `estimated` costs, fills `cost: null` records when the retained routing identity, token usage, and current explicit pricing are sufficient, marks refreshed values as `estimated`, leaves records with missing resources or incomplete pricing unchanged, and persists the whole update atomically with refreshed per-field rule provenance.
* **ACTIVITY-12** A record without a recorded Provider model ID can still be priced through a Global rule for the name the caller sent.
* **ACTIVITY-13** Historical records with a cost but no `cost_source` retain the legacy `reported` interpretation and are never overwritten.
* **ACTIVITY-14** Activity statistics aggregate cost and coverage alongside request and token totals, separately count upstream-reported and locally estimated requests at the overall, time-bucket, Provider, model, and Gateway API-key levels, and the console identifies those sources instead of presenting estimates as upstream-reported spend; a reported or estimated `$0.00` remains distinct from unavailable cost.
* **ACTIVITY-15** The console's valued-request coverage cannot be lower than the sum of reported and estimated source counts, including when reading a transitional statistics response with an absent or inconsistent aggregate coverage field.
* **ACTIVITY-16** SSE usage parsing honors event framing across arbitrary network chunks, supports CRLF and multiline data fields, ignores comments and `[DONE]`, reads OpenAI Responses usage nested under `response`, and combines Anthropic usage split across `message_start` and `message_delta` events.
* **ACTIVITY-17** Activity statistics aggregate exact request, token, success, streaming, latency, and reported-cost totals over a caller-selected time range and support intersecting comma-separated Provider, exact requested-model, and stable Gateway API-key filters while retaining the singular Provider query for compatibility.
* **ACTIVITY-18** Statistics return unfiltered in-range filter options, server-side time buckets with separate input/output token totals plus first-byte and generation totals for successful responses the Provider streamed, per-Provider request buckets, and ranked Provider, model, and Gateway API key dimensions; safe API-key options contain only stable IDs, notes, and masked prefixes, never secrets or hashes.
* **ACTIVITY-19** Overview totals and charts do not silently truncate to the newest 1,000 Request explorer records.
* **ACTIVITY-20** The ranked model dimension groups by either of a request's two model names: by default the caller's requested name, including a public route alias, or the exact final model ID sent to the Provider when the caller passes `model_dimension=outgoing`.
* **ACTIVITY-21** Grouping by the sent model merges every incoming name that reaches the same destination while keeping destination overrides visible, records without a recorded Provider model ID stay visible as one unnamed group rather than disappearing, the console's Model analysis card labels its column and explanatory copy for the selected name and switches without leaving the page, and any other `model_dimension` value is rejected.
* **ACTIVITY-22** Cost and coverage aggregates apply to whichever grouping is selected, while Activity filters, filter options, and the Request explorer remain keyed by the caller's requested name.
* **ACTIVITY-23** Every proxied request that reaches an upstream records the stable ID, current note, and non-secret display prefix of the authenticated Gateway API key, including transport failures and upstream errors; API key secrets and hashes are never recorded, authentication-disabled and historical requests remain explicitly unattributed, and Request explorer search includes this safe key metadata.
* **ACTIVITY-24** The Activity Overview presents request, total-token, cache-hit, success-rate, streaming, average-latency, and reported-cost summaries with sparklines.
* **ACTIVITY-25** The time-bucketed timeline connects exact bucket values with a curve that cannot overshoot local extrema, centers each aggregate value in its matching interactive interval, and uses predictable wall-clock-aligned intervals.
* **ACTIVITY-26** The interval size is chosen per selected range so multi-day ranges keep their within-day shape readable — hourly intervals through 7 days, 2-hour through 14 days, 6-hour through 30 days, daily beyond — while never rendering more than 336 intervals, and short ranges keep their already-fine resolution.
* **ACTIVITY-27** Visible axis labels are thinned to the available chart width so denser intervals cannot crowd the axis, and static point markers appear only while intervals remain individually distinguishable, at least about twelve pixels of plot width per interval, so dense timelines stay a clean line with the inspected interval identified by its hover or focus ring.
* **ACTIVITY-28** The timeline can switch among requests, tokens, and performance: Requests overlays a subdued dashed error-rate curve on an independently scaled percentage axis, Tokens renders separately identified input-token and output-token lines on a shared token scale plus cache-hit rate on a percentage scale, and Performance renders average latency, time to first token, and generation throughput in tok/s on its own right-hand scale whose unit is named in the legend and inspector instead of being repeated on every axis label.
* **ACTIVITY-29** Time to first token and throughput are measured only from successful requests whose Provider response streamed, so a stalled or failed stream cannot dilute them; an interval without that measurement leaves a gap and reports `Not available` instead of plotting a zero, an interval without any request has no average latency to plot and gaps the same way, and throughput is the measured ratio of tokens to generation time rather than a rate inferred from the caller's streaming preference.
* **ACTIVITY-30** In Requests, Tokens, and Performance modes, pointer inspection selects the plotted series nearest the pointer and identifies its corresponding request volume or error rate, input, output, or cache-hit value, or average latency, first-token, or throughput value, instead of always reporting the primary series.
* **ACTIVITY-31** The timeline emphasizes recent changes without dropping empty intervals, remains correctly scaled after ranges are changed from another Activity tab or its container is resized, and lets pointer, keyboard, and touch users inspect each interval's volume, input and output usage, health, latency, cache, and cost, keeping a separator on every wrapped row of that interval detail grid.
* **ACTIVITY-32** A per-model analysis groups by either of a request's two model names and shows request share, input/output usage, cache-hit rate, success, average latency, reported spend, and cost coverage; success rates at or above 99% are healthy, rates from 95% up to 99% are warnings, and rates below 95% are critical, while the exact error count remains visible and Provider and Gateway API key traffic remain independently visible.
* **ACTIVITY-33** Summary cards and timeline details use the available width on desktop, collapse progressively on tablet, and become swipeable or compact on phones without removing the underlying information.
* **ACTIVITY-34** Activity can be filtered by a searchable set of preset time ranges, an exact custom local-time interval, and searchable multi-select Provider, requested-model, and Gateway API-key dimensions; active selections are visible as removable chips, selections within one dimension are ORed, dimensions are intersected, and filters apply consistently to Overview and Request explorer, while the time picker supports arrow-key navigation, Enter selection, and Escape dismissal.
* **ACTIVITY-35** Activity automatically refreshes statistics and requests at a bounded cadence while the page and browser tab are visible, can be refreshed on demand, and can be switched between the visual Overview and a searchable Request explorer with status filtering.
* **ACTIVITY-36** Overview fetches only its small recent-request sample, while the explorer uses server-side search across request, route, model, and safe Gateway API key metadata plus status and Provider, with complete Previous/Next pagination over a stable refresh snapshot and at most 100 rows fetched and rendered at once.
* **ACTIVITY-37** The explorer adapts its usable list height to the viewport and emphasizes the incoming and outgoing model names, route, status, latency, and token output while retaining secondary metadata.
* **ACTIVITY-38** Selecting a request opens a right-side, full-height detail drawer on desktop or a contained responsive dialog on narrow screens, grouping model route, API formats, destination, authenticated Gateway API key identity, request ID, API path, and Provider finish reason into one routing section with readable labels, values, and supporting text no smaller than 10px at any supported viewport.
* **ACTIVITY-39** The detail uses one full-width fact per row with desktop labels and values kept together horizontally, and shows status, a shared-scale request-stage waterfall with exactly aligned scale and track boundaries, total latency once in the section heading without a duplicate total row, token usage, derived output throughput, and cost while reiterating that prompt and response content are not retained.
* **ACTIVITY-40** When cost is unavailable the detail panel offers a direct centralized pricing action prefilled with the model name the caller sent as a Global incoming price, and an estimated cost lists which rule supplied each rate.
* **ACTIVITY-41** Activity remains immediately queryable in memory and is batch-written after 10 records or 60 seconds rather than writing every request synchronously, and pending records are flushed when Yabane completes graceful shutdown.
* **ACTIVITY-42** Normal Activity flushes append JSON Lines instead of rewriting the full history, and each periodic flush atomically compacts records older than the persisted retention policy, defaulting initially to 30 days, even when no new requests arrive.
* **ACTIVITY-43** Activity data management uses a dedicated dialog: export requires choosing a time range and previews record count, estimated size, and oldest and newest timestamps before download.
* **ACTIVITY-44** An administrator can export retained Activity as a timestamp-named, versioned Yabane JSON file and import it into another instance without requiring matching Provider or Endpoint configuration, and imported routing metadata remains visible as originally recorded.
* **ACTIVITY-45** Before an Activity import writes anything, the console validates the selected file and previews its size plus total, new, already-present, and outside-retention record counts; invalid files remain visibly rejected with `400`, a persistence failure logs its local detail and returns a generic `500` without publishing records in memory, and the completed import reports its final outcome in the same dialog.
* **ACTIVITY-46** Every installation persists a random Activity instance ID, and import is idempotent by source instance ID plus request ID, so repeated and transitive imports are skipped without treating coincident request IDs from different instances as the same record.

* **SAFETY-02** Authenticated admin gateway API-key list responses expose generated secrets for reveal and copy but never expose secret hashes.
